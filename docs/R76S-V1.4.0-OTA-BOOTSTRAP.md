# R76S-V1.4.0 OTA bootstrap fix

## Root cause

The V1.4.0 installer writes `sysupgrade -b` directly to
`/tmp/r76s-ota/configuration.tar.gz`. It does not use a `.part` file, does
not require a non-zero archive, and does not validate the archive before the
flash launch. A repeated LuCI install request can therefore race on the same
path and leave a zero-byte archive.

The V1.4.0 transaction lock is only an unowned directory. It has no PID or
transaction record, and the install error path can leave it behind. The next
request then reports `OTA busy` forever. The controller also has no install
request lock, so duplicate HTTP requests reach the backend.

## Minimal application

Run `scripts/r76s-v140-ota-bootstrap-fix.sh` on the running
R76S-V1.4.0 system with root privileges. It only backs up and replaces the
V1.4.0 OTA launcher and adds a configuration-backup helper. It does not read,
replace, or download `/tmp/firmware.img`, and it never invokes the real
`sysupgrade` flash command.

Apply it while no old OTA backup or flash process is active. The verified
`phase=verified` state described in the incident is the safe point; an
already-running legacy transaction should be allowed to finish or be stopped
before installing the wrapper.

The helper starts exactly one `sysupgrade -b` process, writes
`configuration.tar.gz.part`, requires rc=0 and a non-zero size, validates it
with `tar -tzf`, and atomically renames it to `configuration.tar.gz`.
Stale locks are reclaimed by PID/cmdline validation. Any backup failure exits
before the original installer can enter its flash launch path.

After the script prints `R76S OTA bootstrap fix applied`, return to LuCI and
click “在线升级并保留配置”. Do not click the button twice.
